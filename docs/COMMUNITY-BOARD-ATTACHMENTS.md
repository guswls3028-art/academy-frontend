# 커뮤니티 게시물 사진·첨부파일 등록 계약

## 목적과 진입 경로

관리자·선생님은 `/workspace/community/notice`와 `/workspace/community/board`에서
게시 대상을 선택하고 제목, 본문, 사진을 포함한 첨부파일을 한 번에 등록한다. 첨부
사진은 본문 안의 base64 인라인 이미지가 아니라 게시물 상세의 정식 첨부파일로
저장되고, 학생 상세 재조회와 새로고침 뒤에도 표시되어야 한다.

공지 작성 화면의 리치 텍스트 편집기 이미지 선택·붙여넣기·드롭은 첨부파일 상태로
전달한다. 공용 편집기는 `data:image/...` URL을 본문에 생성하지 않는다. 서버는
보안을 위해 `data:` URL을 HTML 정제 단계에서 제거하므로, 첨부 업로드 콜백이 없는
화면에서는 이미지를 저장된 것처럼 본문에 미리 보이지 않고 지원 불가 안내를 낸다.

## 작성과 저장 흐름

1. 사용자가 전체·강의·차시 중 게시 대상을 선택한다.
2. 제목과 본문을 작성한다. 공지는 편집기의 이미지·파일 버튼, 이미지 붙여넣기 또는
   드롭을 사용하고, 게시판은 `+ 파일 추가`를 사용해 파일을 최대 10개 선택한다.
3. 파일 입력의 브라우저 값을 초기화하기 전에 선택한 `File` 목록을 복사해 React
   상태에 보관한다. 따라서 파일을 먼저 고른 뒤 본문을 작성해도 선택 목록이
   사라지지 않는다.
4. 등록 시 게시물 생성 요청을 먼저 보내고, 반환된 게시물 ID로 첨부파일을
   업로드한다.
5. 두 요청이 모두 성공하면 새 게시물 상세로 이동한다. 상세의 첨부파일 목록과
   새로고침 후 재조회가 서버에 저장된 파일 이름을 보여 주어야 한다.

## 실패와 재시도

- 게시물 생성이 실패하면 생성된 게시물 ID가 없으므로 일반 등록 오류를 표시하고
  같은 작성 폼에서 다시 등록한다.
- 공지나 게시물은 생성됐지만 첨부 업로드가 실패하면 제목·본문·선택 파일을 유지하고
  `첨부 다시 시도`를 표시한다. 제목과 본문은 이미 저장된 값과 화면 값이 갈라지지
  않도록 재시도 동안 읽기 전용이다. 파일 입력과 추가·제거도 잠가 최초 요청과
  동일한 파일 집합만 재시도할 수 있게 한다.
- 첨부 재시도는 기존 게시물 ID만 사용하며 게시물 생성 요청을 다시 보내지 않는다.
  최초 첨부 시도와 재시도는 같은 클라이언트 요청 키를 사용해 네트워크 결과가
  불명확하거나 서버 저장 뒤 응답만 유실된 경우에도 중복 첨부를 막는다. 게시물 생성
  뒤 파일 집합을 바꾸려면 현재 재시도를 완료하고 상세의 첨부 관리 기능을 사용한다.

백엔드의 테넌트, 권한, 원자적 업로드 규칙은
[커뮤니티 도메인 계약](../../backend/docs/domain/community.md)이 소유한다.

## 권한과 테넌트 경계

- 프런트엔드는 로그인한 사용자의 현재 테넌트와 선택한 게시 범위를 요청에
  전달할 뿐, 기본 테넌트를 추론하거나 다른 테넌트 게시물을 대신 선택하지 않는다.
- 게시물 작성과 첨부 업로드 권한은 백엔드가 동일하게 검사한다. 관리자·선생님은
  허용된 범위에 작성할 수 있고, 학생은 자신이 작성할 수 있는 범위와 소유권 안에서만
  동작하며, 학부모는 읽기 전용이다.
- 존재하지만 현재 사용자가 볼 수 없는 게시물은 첨부 대상이 될 수 없다.

## 화면 상태와 반응형 계약

- 선택 파일 이름과 개수는 등록 전, 첨부 실패 후, 재시도 중에 계속 보인다.
- 재시도 버튼은 처리 중 비활성화되고 `첨부 재시도 중…`으로 바뀐다.
- 오류에는 게시물 저장 성공과 첨부 실패를 구분해 안내한다.
- 1366px 데스크톱과 390px 모바일에서 작성 폼, 파일 목록, 오류, 재시도 버튼이
  가로로 넘치지 않아야 한다.

### QnA 첨부 열람

- 학생 또는 선택 자녀 범위의 학부모가 질문에 올린 첨부는 질문 상세를 다시 조회하거나
  새로고침한 뒤에도 파일 이름과 크기를 유지한다.
- 관리자 QnA 답변 화면은 이미지 첨부를 회전·확대 가능한 문제 보기로 표시하고,
  PDF·문서 등 비이미지 첨부는 파일 형식, 원본 이름, 크기와 다운로드 동작이 있는
  별도 목록으로 표시한다. 비이미지 파일이 있다는 이유로 `첨부된 문제 사진이
  없습니다` 빈 상태를 표시하지 않는다.
- 다운로드 URL은 화면에 저장하거나 추론하지 않는다. 사용자가 파일 버튼을 누를 때
  현재 로그인·테넌트·선택 자녀 범위로 첨부 다운로드 API를 호출하고, 반환된 presigned
  URL은 공용 안전 다운로드 유틸리티로 연다. URL 조회가 실패하면 파일 항목을 유지하고
  오류를 안내한다.
- 관리자·학생·학부모 상세 화면은 키보드로 파일 버튼을 실행할 수 있어야 하며, 390px에서도
  파일 이름이나 다운로드 동작 때문에 가로 스크롤이 생기지 않아야 한다.

### 삭제와 원본 파일 정리

- 게시물·첨부 DELETE의 정상 완료는 `204`다. 프런트엔드는 삭제된 상세를 닫고 해당
  게시물 종류의 목록, 상세, 건수·알림 query만 다시 조회한다.
- 서버가 논리 DB 삭제를 완료했지만 R2 원본 정리가 남으면 `502`와
  `community_storage_cleanup_pending`을 반환한다. 프런트엔드는 이 응답을 오직
  `detail`, `deleted`, `storage_cleanup`의 모든 count가 0 이상의 정수이고,
  게시물 DELETE는 `deleted.posts=1`, 첨부 DELETE는
  `deleted.posts=0`, `deleted.attachments=1`일 때만 부분 완료로 인정한다.
  `storage_cleanup.pending + storage_cleanup.failed`도 1 이상이어야 한다.
- `pending`과 `failed`는 서로 겹치지 않는 원본 수다. 화면은 합계를 미완료 원본 수로
  표시하고 두 count를 나눠 안내한다. 다른 소유자가 있어 보호된 파일은 서버의
  `cleaned`에 포함되지 않으며, 프런트엔드는 응답 밖의 정리 결과를 추정하지 않는다.
- 정확한 부분 완료 응답은 이미 DB 대상이 사라졌으므로 일반 실패처럼 상세에 남기거나
  DELETE를 자동 재전송하지 않는다. 목록·상세·건수를 갱신하고 화면을 이전 작업 맥락으로
  돌린 뒤, backend `detail`과 미완료 원본 수 및 동일 삭제 재시도 금지를 안내한다.
- count가 맞지 않거나 필드가 빠진 `502`, 일반 `403`·`404`·`409`, 네트워크 오류는
  삭제 성공으로 바꾸지 않는다. 상세를 유지하고 기존 오류 복구 동선을 사용한다.
- 선생 앱의 작성 중 첨부 업로드 실패 뒤 보상 DELETE가 `204` 또는 정확한 부분 완료로
  끝나면 게시물 목록을 다시 조회한다. 이 경우에도 사용자에게 보이는 주 오류는 원래
  첨부 업로드 실패이며, 부분 완료라면 원본 정리 상태를 같은 오류 안내에 덧붙인다.

## 검증

게시판 회귀 사양은 `e2e/admin/board-photo-persistence.mock.spec.ts`, 공지 이미지
회귀 사양은 `e2e/admin/community-workspace-polish.mock.spec.ts`가 소유한다. 두 사양은
파일 선택 후 본문에 base64가 남지 않는지, 서버 저장 뒤 첫 첨부 응답 유실, 파일
집합 동결, 같은 게시물·파일·요청 키로의 재시도, 중복 게시물 없음, 상세·새로고침
지속성, 데스크톱·390px 무가로넘침을 검증한다.

`e2e/admin/community-workspace-polish.mock.spec.ts`는 QnA의 이미지 보기와 함께
비이미지 첨부가 관리자 화면에 나타나는지, 학생·학부모가 새로고침 뒤에도 같은 파일을
열고 다운로드 URL을 요청하는지, 학부모 요청이 선택 자녀 헤더를 유지하는지도 검증한다.
같은 사양과 `e2e/teacher/comms-reply-mobile.mock.spec.ts`는 정상 `204`, endpoint별 exact
부분 완료 count, 잘못된 `502` 거부, 삭제 상세 닫기·목록 재조회와 DELETE 1회만 전송도
검증한다.

```powershell
$env:E2E_BASE_URL='http://127.0.0.1:<owned-port>'
pnpm exec playwright test e2e/admin/board-photo-persistence.mock.spec.ts --project=chromium
pnpm exec playwright test e2e/admin/community-workspace-polish.mock.spec.ts --grep "공지 이미지를" --project=chromium
```
