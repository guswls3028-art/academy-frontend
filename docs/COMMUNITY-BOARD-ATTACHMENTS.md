# 커뮤니티 게시물 사진·첨부파일 등록 계약

## Q&A 질문 자료 확인

관리자·선생님은 `/workspace/community/qna`에서 학생 질문의 이미지와 일반 첨부파일을
함께 확인한다. 질문 자료의 개수는 모든 첨부를 포함하며, 이미지 미리보기는 게시물
상세 응답의 URL을 사용한다. PDF 등 일반 파일과 미리보기를 열 수 없는 이미지는
파일명·크기와 **다운로드**를 표시한다. 다운로드할 때마다 현재 로그인·테넌트 권한으로
`/api/v1/community/posts/:postId/attachments/:attachmentId/download/`에서 새 서명 URL을
받고, 사용자가 누른 파일만 내려받는다. 권한 거절이나 URL 조회 실패는 파일 행에
오류를 남기고 같은 버튼으로 재시도한다. 이미지가 없거나 로딩에 실패하면 **다시 보기**로
새 URL을 받아 미리보기를 복구하거나 다운로드할 수 있다. 다른 이미지는 계속 표시한다.
여러 이미지를 동시에 복구해도 응답한 파일의 사진을 정확히 선택하며, 다른 이미지의
실패로 목록 순서가 바뀌어도 현재 보고 있는 사진의 선택을 유지한다.
질문을 새로고침해도 첨부 목록은 서버의 게시물 상세 응답에서 복원하며, 390px과
데스크톱 모두 답변 작성 동선을 유지한다. 파일별 진행·실패 상태는 독립적이며,
같은 파일의 중복 요청을 막고 질문을 전환한 뒤 도착한 다운로드 응답은 실행하지 않는다.
회귀 검증은 `e2e/admin/community-workspace-polish.mock.spec.ts`가 소유한다.
동일 배포 산출물의 격리 실사용 `e2e/student/student-parent-community-realuse.spec.ts`는
학부모가 선택한 자녀의 이미지·일반 파일 업로드 복구부터 관리자 PC·390px 원본
다운로드 bytes, 새로고침, 다른 자녀 격리와 첨부 포함 정리까지 검증한다.
QA 다운로드 경계는 인증된 게시물·첨부 ID·파일명·크기를 먼저 확인하고, 해당 개발
테넌트/게시물의 정확한 PDF/TXT 서명 URL만 전달한다. 운영 버킷·다른 테넌트·리다이렉트·
앱 자격증명 전달·크기/형식 불일치는 거절하며, 이미지 읽기 경계는 그대로 유지한다.

## 목적과 진입 경로

관리자·선생님은 `/workspace/community/notice`와 `/workspace/community/board`에서
게시 대상을 선택하고 제목, 본문, 사진을 포함한 첨부파일을 한 번에 등록한다. 첨부
사진은 본문 안의 base64 인라인 이미지가 아니라 게시물 상세의 정식 첨부파일로
저장되고, 학생 상세 재조회와 새로고침 뒤에도 표시되어야 한다.

공지 작성 화면의 리치 텍스트 편집기 이미지 선택·붙여넣기·드롭은 첨부파일 상태로
전달한다. 공용 편집기는 `data:image/...` URL을 본문에 생성하지 않는다. 서버는
보안을 위해 `data:` URL을 HTML 정제 단계에서 제거하므로, 첨부 업로드 콜백이 없는
화면에서는 이미지를 저장된 것처럼 본문에 미리 보이지 않고 지원 불가 안내를 낸다.

## 작성과 저장 흐름

### 기존 공지의 정정·사진 추가

공지 상세의 **수정**에서도 새 공지와 동일하게 사진 선택·붙여넣기·드롭과 파일
첨부를 지원한다. 선택한 사진은 저장 전 미리보기와 파일명·크기로 확인하고 제거할
수 있다. 본문을 바꾸지 않고 사진만 추가해도 저장할 수 있다. 이미지는 본문 아래
정식 첨부 목록에 표시되며 학생 화면과 새로고침에서도 유지된다. 기존 첨부까지
합해 최대 10개, 이미지 5MB·일반 파일 50MB이며 초과·중복 선택은 안내한다.

저장은 변경된 본문 PATCH 다음 첨부 업로드 순서다. 본문 실패 시 파일과 초안을
유지한다. 첨부 실패 시 저장된 본문을 다시 PATCH하지 않고 같은 파일·요청 키로
**첨부 다시 시도**한다. 결과가 불명확한 동안 파일 변경을 막고, 업로드 전 검증
거절(400)일 때만 파일을 고쳐 다시 제출할 수 있다. 취소 시 이미 저장된 본문과
첨부 결과를 재조회한다. 저장 중 본문 편집을 막고 제목·고정 상태 재조회는 미저장
본문을 덮어쓰지 않는다. 제목은 키보드로 수정할 수 있고 한글 조합 중 Enter는
저장하지 않는다. 목록 복귀와 브라우저 종료에는 수정 중 이탈 안내를 제공한다.

상세에는 기존 첨부의 이미지 미리보기·다운로드·확인 후 삭제를 제공한다. 만료되거나
실패한 미리보기는 **다시 보기**로 현재 권한의 새 URL을 받는다. 다운로드도 매번
새 URL을 받으며 게시물 전환 후 도착한 응답을 실행하지 않는다. 각 파일의 오류와
재시도는 독립적이고 390px에서 이름과 버튼이 화면 밖으로 넘치지 않아야 한다.
짧은 첨부 표시 전환은 reduced-motion 설정을 따른다.

회귀는 `e2e/admin/community-workspace-polish.mock.spec.ts`가 사진만 추가,
응답 유실 재시도, 본문 오류·제목 재조회 후 초안 보존을 검사한다. 동일 산출물 개발
실사용 `e2e/flows/notice-roundtrip.spec.ts`는 관리자 UI 작성 → 기존 공지 사진 추가
→ PC/390px 재조회 → 학생 이미지 로딩·새로고침 → 첨부 포함 삭제를 검증한다.

### 새 게시물 등록

교사용 모바일 상세의 **편집**도 서식 편집기에서 사진 선택·붙여넣기·드롭을 지원한다.
제목·본문이 바뀐 경우에만 먼저 저장하고, 사진만 추가한 경우에는 첨부만 저장한다.
첨부 응답 실패는 파일과 요청 키를 유지하며 재시도 때 본문을 다시 저장하지 않는다.
취소는 현재 서버 상태를 재조회하며 미저장 변경이 있으면 이탈 확인을 제공한다.
`comms-reply-mobile.mock.spec.ts`가 부분 저장 재시도를, 동일 산출물 실사용
`board-attachments-realuse.spec.ts`가 모바일 작성·수정·재조회와 학생 접근을 검사한다.

1. 사용자가 전체·강의·차시 중 게시 대상을 선택한다.
2. 제목과 본문을 작성한다. 공지·게시판·자료실은 편집기의 이미지 버튼, 이미지
   붙여넣기·드롭 또는 `+ 파일 추가`로 최대 10개를 선택한다. 학생 질문·상담과
   교사용 모바일 작성도 편집기 첨부를 같은 정식 파일 업로드에 연결한다.
3. 파일 입력의 브라우저 값을 초기화하기 전에 선택한 `File` 목록을 복사해 React
   상태에 보관한다. 따라서 파일을 먼저 고른 뒤 본문을 작성해도 선택 목록이
   사라지지 않는다.
4. 등록 시 게시물 생성 요청을 먼저 보내고, 반환된 게시물 ID로 첨부파일을
   업로드한다.
5. 두 요청이 모두 성공하면 새 게시물 상세로 이동한다. 상세의 첨부파일 목록과
   새로고침 후 재조회가 서버에 저장된 파일 이름을 보여 주어야 한다.

## 실패와 재시도

- 게시물 생성이 실패하면 생성된 게시물 ID가 없으므로 일반 등록 오류를 표시하고
  같은 작성 폼에서 다시 등록한다.
- 공지나 게시물은 생성됐지만 첨부 업로드가 실패하면 제목·본문·선택 파일을 유지하고
  `첨부 다시 시도`를 표시한다. 제목과 본문은 이미 저장된 값과 화면 값이 갈라지지
  않도록 재시도 동안 읽기 전용이다. 파일 입력과 추가·제거도 잠가 최초 요청과
  동일한 파일 집합만 재시도할 수 있게 한다.
- 첨부 재시도는 기존 게시물 ID만 사용하며 게시물 생성 요청을 다시 보내지 않는다.
  최초 첨부 시도와 재시도는 같은 클라이언트 요청 키를 사용해 네트워크 결과가
  불명확하거나 서버 저장 뒤 응답만 유실된 경우에도 중복 첨부를 막는다. 게시물 생성
  뒤 파일 집합을 바꾸려면 현재 재시도를 완료하고 상세의 첨부 관리 기능을 사용한다.

백엔드의 테넌트, 권한, 원자적 업로드 규칙은
[커뮤니티 도메인 계약](../../backend/docs/domain/community.md)이 소유한다.

## 권한과 테넌트 경계

- 프런트엔드는 로그인한 사용자의 현재 테넌트와 선택한 게시 범위를 요청에
  전달할 뿐, 기본 테넌트를 추론하거나 다른 테넌트 게시물을 대신 선택하지 않는다.
- 게시물 작성과 첨부 업로드 권한은 백엔드가 동일하게 검사한다. 관리자·선생님은
  허용된 범위에 작성할 수 있고, 학생은 자신이 작성할 수 있는 범위와 소유권 안에서만
  동작한다. 학부모의 일반 게시판·자료실은 읽기 전용이며, 질문·상담은 기존 선택
  자녀 권한과 초안 격리 계약에 따라 작성한다.
- 존재하지만 현재 사용자가 볼 수 없는 게시물은 첨부 대상이 될 수 없다.

## 화면 상태와 반응형 계약

- 선택 파일 이름과 개수는 등록 전, 첨부 실패 후, 재시도 중에 계속 보인다.
- 재시도 버튼은 처리 중 비활성화되고 `첨부 재시도 중…`으로 바뀐다.
- 오류에는 게시물 저장 성공과 첨부 실패를 구분해 안내한다.
- 1366px 데스크톱과 390px 모바일에서 작성 폼, 파일 목록, 오류, 재시도 버튼이
  가로로 넘치지 않아야 한다.

### 삭제와 원본 파일 정리

- 게시물·첨부 DELETE의 정상 완료는 `204`다. 프런트엔드는 삭제된 상세를 닫고 해당
  게시물 종류의 목록, 상세, 건수·알림 query만 다시 조회한다.
- 서버가 논리 DB 삭제를 완료했지만 R2 원본 정리가 남으면 `502`와
  `community_storage_cleanup_pending`을 반환한다. 프런트엔드는 이 응답을 오직
  `detail`, `deleted`, `storage_cleanup`의 모든 count가 0 이상의 정수이고,
  게시물 DELETE는 `deleted.posts=1`, 첨부 DELETE는
  `deleted.posts=0`, `deleted.attachments=1`일 때만 부분 완료로 인정한다.
  `storage_cleanup.pending + storage_cleanup.failed`도 1 이상이어야 한다.
- `pending`과 `failed`는 서로 겹치지 않는 원본 수다. 화면은 합계를 미완료 원본 수로
  표시하고 두 count를 나눠 안내한다. 다른 소유자가 있어 보호된 파일은 서버의
  `cleaned`에 포함되지 않으며, 프런트엔드는 응답 밖의 정리 결과를 추정하지 않는다.
- 정확한 부분 완료 응답은 이미 DB 대상이 사라졌으므로 일반 실패처럼 상세에 남기거나
  DELETE를 자동 재전송하지 않는다. 목록·상세·건수를 갱신하고 화면을 이전 작업 맥락으로
  돌린 뒤, backend `detail`과 미완료 원본 수 및 동일 삭제 재시도 금지를 안내한다.
- 선생 앱의 상담 메모 삭제도 같은 커뮤니티 게시글 DELETE 계약을 사용한다. 부분 완료 시
  메모 상세를 닫고 목록을 다시 조회하며 원본 정리 대기를 알린다.
- count가 맞지 않거나 필드가 빠진 `502`, 일반 `403`·`404`·`409`, 네트워크 오류는
  삭제 성공으로 바꾸지 않는다. 상세를 유지하고 기존 오류 복구 동선을 사용한다.
- 선생 앱의 첨부 실패 뒤 보상 DELETE는 제거했다. 응답 유실만으로 이미 저장된
  사용자 글을 삭제하지 않고 동일 글·원자적 첨부 배치·요청 키를 재시도한다.
  취소해도 저장된 글은 남고 목록을 갱신한다. 기존 사용자 데이터의 정리·이관은 없다.

## 다른 작성·수정 화면의 저장 경계

일반 게시판·자료실은 `PostCreatePane`, `PostContentEditor`, `PostAttachmentManager`를
공유한다. 수정 중 사진만 추가해도 저장되며, 본문 PATCH 성공 뒤 첨부만 실패하면
PATCH를 반복하지 않는다. 제목이나 첨부 목록 재조회가 수정 중인 본문을 초기화하지
않는다. 상세의 별도 파일 추가는 미리보기 확인 후 **첨부 저장**하며 실패 시 선택 파일과
같은 키를 유지한다. 400 검증 거절만 파일 교체를 허용하고 다른 불명확한 결과는
동일 파일로 재시도한다. 자료실도 등록 후 생성된 글 상세로 이동한다.

학생 Q&A·상담은 기존 테넌트·계정·선택 자녀별 초안 및 배치 복구 계약을 유지한다.
편집기와 파일 선택의 이미지 5MB/일반 파일 50MB 한도를 통일하고, 미확정 배치를
바꾸지 않도록 잠근다. 홈페이지 학원 커뮤니티(`/landing/community/.../write`)는
사진 최대 5장/5MB를 유지한다. 첨부 실패를 완료로 처리하지 않고 글 ID·파일 메타·
요청 키를 소유자별 초안에 보관한다. reload 후 원래 사진을 같은 순서로 재선택하면
같은 글의 첨부만 재시도한다. 사진 바이트는 브라우저 초안 저장소에 쓰지 않는다.
학원 커뮤니티 상세에서도 저장된 사진을 본문 아래 표시하고 실패한 주소는 재조회한다.
자료실 목록 갱신 중에는 방금 저장한 글 선택을 해제하지 않으며, 편집기에서 j/k를
입력하는 동안 목록 단축키가 다른 글로 이동시키지 않는다.

별도 공개 게시판(`/landing/board`) 작성·수정과 수강후기(`/landing/reviews`)는
공개 사진 선택/미리보기/제거를 제공한다. PNG/JPG/WebP 최대 8장, 한 장 5MB이며
공개 게시판 편집기의 선택·붙여넣기·드롭도 이 목록으로 연결된다. 사진 업로드를
모두 마친 뒤 글을 저장한다. 실패하면 본문·사진을 유지하고 이미 완료한 파일은
다시 업로드하지 않는다. 저장 중 입력을 잠가 전송 데이터와 화면 값의 차이를 막는다.
작성자의 수정 및 승인 전 후기 조회는 인증된 상세 API를 사용한다.

공개 사진은 서버의 안정적인 키를 저장하고 상세에서 새 서명 URL로 표시한다.
오류 시 **사진 다시 보기**로 조회하며 기존 원본 열기도 제공한다. 구 URL 데이터와
권한·테넌트·승인 정책은 backend `docs/domain/community.md`가 소유한다. 백엔드를
먼저 배포하고 프런트를 승격한다. 공개 글 생성 자체의 응답 유실을 정확히 한 번의
생성으로 보장하는 새 API는 이 변경에 포함하지 않는다.

답변·댓글 `PostReply`는 본문 API만 있고 파일 소유·저장 API가 없다. 이 화면의
실행되지 않는 이미지 버튼과 잘못된 "이미지 첨부 가능" 문구는 제거했다. 공지·게시판·
자료실·질문·상담의 실제 첨부 지원은 위 경로로 복구했으며, 공통 편집기는 업로드
콜백이 연결된 경우에만 이미지·파일 선택을 제공한다. 기존 본문과 서식은 유지하고
답변 저장 중 새 입력이 성공 콜백에 의해 지워지지 않도록 전송 중 입력을 잠근다.

## 검증

게시판 회귀 사양은 `e2e/admin/board-photo-persistence.mock.spec.ts`, 공지 이미지
회귀 사양은 `e2e/admin/community-workspace-polish.mock.spec.ts`가 소유한다. 두 사양은
파일 선택 후 본문에 base64가 남지 않는지, 서버 저장 뒤 첫 첨부 응답 유실, 파일
집합 동결, 같은 게시물·파일·요청 키로의 재시도, 중복 게시물 없음, 상세·새로고침
지속성, 데스크톱·390px 무가로넘침을 검증한다.

동일 산출물 개발 실사용은 `e2e/flows/notice-roundtrip.spec.ts`에서 관리자 작성→기존
공지에 사진만 추가→저장·reload→학생 이미지 로딩·reload와 정확한 생성 글 정리를 검증한다.
인증된 공지 상세 응답에 묶인 QA 첨부만 읽는 검증 환경의 경계는
[배포·E2E 운영 계약](DEPLOYMENT-OPERATIONS.md)이 소유한다.

`e2e/admin/community-workspace-polish.mock.spec.ts`와
`e2e/teacher/comms-reply-mobile.mock.spec.ts`는 정상 `204`, endpoint별 exact
부분 완료 count, 잘못된 `502` 거부, 삭제 상세 닫기·목록 재조회와 DELETE 1회만 전송도
검증한다.

```powershell
$env:E2E_BASE_URL='http://127.0.0.1:<owned-port>'
pnpm exec playwright test e2e/admin/board-photo-persistence.mock.spec.ts --project=chromium
pnpm exec playwright test e2e/admin/community-workspace-polish.mock.spec.ts --grep "공지 이미지를" --project=chromium
```
